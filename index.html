Webhook Delivery System

Challenge

Webhook delivery requires guaranteed async processing, retry logic on failure, full audit trails, and operational visibility, none of which you get from a simple HTTP call inside an API handler. Built on a producer/consumer architecture with Redis as the message queue.

Approach

  • Two-tier AWS architecture: application layer (FastAPI, RQ worker, Redis, Nginx) on Instance 1, data and observability layer (PostgreSQL, Prometheus, Grafana) on Instance 2, communicating exclusively over a private VPC network. No internal traffic crosses the public internet.
  • Decoupled delivery pipeline: API accepts the event, persists to PostgreSQL, and pushes a job to Redis, returning immediately. The RQ worker processes delivery asynchronously, retrying on failure. Every attempt is recorded. The API never blocks on delivery.
  • Runtime secrets fetched from AWS Parameter Store via IAM role at deploy time. No secrets on disk, no secrets in the repository. GitHub Secrets used only for CI/CD pipeline operations.
  • Four-job GitHub Actions pipeline: test, build, deploy-staging (auto), deploy-production (manual approval gate). Single Docker image, different entrypoint commands for API and worker: one build artifact, two runtime roles.
  • Prometheus scrapes four targets (API, node-exporter, redis-exporter, self). Two active alert rules: target-down fires immediately, high error rate fires when 4xx/5xx ratio exceeds 5% over a 5-minute window.

Outcome

Demonstrates a private two-tier AWS design, asynchronous delivery with retries and audit records, and alerting on failures and error rates.

Production Waitlist API Infrastructure

Challenge

Production APIs need secure HTTPS access, reverse proxy routing, isolated environments, and reliable deployments. A single container exposed directly to the internet is not production-ready.

Approach

  • Built a production-grade FastAPI system with PostgreSQL backend, Nginx reverse proxy, and HTTPS via Let’s Encrypt.
  • Nginx handles SSL termination and forwards traffic internally to FastAPI over a private Docker network. Application and database containers are never publicly exposed.
  • Full GitHub Actions pipeline with staging deployment, production approval gate, health checks, SHA-based rollback, and environment-specific Nginx configurations.

Outcome

Operationalizing an Existing Application

Challenge

Existing applications often lack deployment automation, environment isolation, and operational reliability. Production infrastructure must be designed around software that was not originally built for deployment workflows.

Staging & Production Environment Separation

Challenge

Deploying directly to production on every push means users are exposed to every bug. There is no safe place to test before it’s live.

Approach

  • Two isolated EC2 environments: staging deploys automatically on every push, production requires manual approval.
  • Single Docker image built once and deployed identically to both environments, so there is no drift between staging and production.
  • Per-environment secrets via GitHub Environments. Staging and production have completely isolated credentials.

Multi-Container System with Database

Challenge

Real apps need databases. Running an app and a database together in production requires careful networking, configuration, and startup ordering.

Approach

  • Flask API and PostgreSQL running as separate containers connected via Docker Compose networking.
  • Containers discover each other by service name: no hardcoded IPs, no fragile config.
  • All secrets injected at runtime via environment variables, never stored in code or images.

Docker-Based CI/CD Pipeline

Challenge

Deploying raw code to a server means the server must be configured for every app. One wrong dependency breaks everything.

Approach

  • Containerised a Python Flask app with Docker. The server only needs Docker installed, nothing else.
  • Three-job pipeline: tests run inside the container, image pushed to Docker Hub tagged with Git commit SHA, EC2 pulls and runs the image.
  • Automatic rollback to previous image by SHA if health check fails after deploy.
